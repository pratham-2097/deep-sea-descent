Deep-Sea Descent

by Pratham Prabhu · Computer Graphics I, Project 1

Play it Source code on GitHub Demo video

Deep-Sea Descent is a small underwater scene you can swim through. You glide past coral, jellyfish and bubbles on a checkerboard seafloor. Everything on screen is drawn by my own code on an HTML canvas, with no WebGL and no graphics libraries. The project has four levels, and each one adds a step of the graphics pipeline: from a plain wireframe to filled triangles on a mock 320 x 200 display.

1. Design

I wanted a scene that felt calm and a bit mysterious, where the point is to drift around and look at things. An underwater world fit that well. It also worked with the project's rules: no rotation, simple shapes only, and a fixed camera that just slides around. Coral, jellyfish and bubbles can all be built from pyramids, boxes and diamonds, so the scene still reads as "underwater" even with blocky geometry.

What I planned

  • The look: dark blue water with a checkerboard seafloor running off into the distance. Things fade into the water color as they get farther away, so it feels deep.
  • The objects: four types, each built once and then copied around the scene at different positions and sizes.
    • Coral: a tall pyramid with a small box beside it, in orange and pink.
    • Jellyfish: a pyramid bell on a flat slab, with five tentacles hanging down. They slowly bob up and down.
    • Bubbles: small diamond shapes (octahedrons).
    • Seafloor tiles: flat squares in two shades of blue, laid out like a checkerboard.
  • How it behaves: you control a camera that slides left/right and forward/back (plus up/down). It never turns. You can release bubbles that float upward, and the camera can't pass through coral or jellyfish.
  • Levels: the same scene four ways, so you can see each step of the rendering process: a test cube, a wireframe, a low-res wireframe with my own lines, and filled triangles.

A few more things happen on their own:

  • The jellyfish bob up and down, each one slightly out of step with the others.
  • Released bubbles float up and drift forward, then disappear near the top.
  • If you swim into a coral or jellyfish, the camera stops. If it can still slide sideways or forward, it does.
  • Anything behind the camera, or too close to it, isn't drawn. That stops shapes from flipping or stretching across the screen.

4. How it works

Every frame goes through the same pipeline. Only the last step changes between levels.

model (vertices, edges, triangles)
   │  scale it, then move it to its position   (instance)
   ▼
world position
   │  subtract the camera position
   ▼
camera-relative position (x, y, z)
   │  u = x / z,  v = y / z                     (pinhole camera)
   ▼
screen position
   │
   ├─ Level 1 → canvas lines on 1600 x 1000
   ├─ Level 2 → my own line function → 320 x 200 pixel array
   └─ Level 3 → triangle fill + depth buffer → 320 x 200 pixel array
                                       │
                                       ▼
                          draw each pixel as a 5 x 5 square

4.1 3D objects as vertices and edges

Each object type is defined once, centered at the origin, as a list of vertices (3D points) and edges (pairs of vertex numbers to join with a line). For level 3, the same shapes also get a list of triangles (three vertex numbers each). For example, a box has 8 corners, 12 edges, and 12 triangles, since each of its 6 faces is split into 2 triangles.

To place objects in the scene, I make instances. Each instance stores which model it uses, a position vector, a scale factor and a color. To get a vertex's world position, I multiply the model vertex by the scale and then add the position. There's no rotation, only scaling and translation. That's how one coral model becomes 14 corals of different heights.

Example: a coral model vertex at (0, 1, 0), with scale 1.5 and position (2, 1.5, 7):
world = (0 × 1.5 + 2, 1 × 1.5 + 1.5, 0 × 1.5 + 7) = (2, 3, 7)

4.2 Pinhole camera projection

A pinhole camera sees things farther away as smaller. To fake that on a flat screen, I first move everything so the camera sits at (0, 0, 0) by subtracting the camera's position. Then I divide by depth: u = x / z and v = y / z. A point that's twice as far away ends up half as far from the center of the screen. Finally I stretch u and v to fit the canvas, and flip v, because canvas y counts downward.

function project(vertex, obj, screenW, screenH) {
  const x = vertex[0] * obj.scale + obj.position[0] - camera.x;
  const y = vertex[1] * obj.scale + obj.position[1] - camera.y;
  const z = vertex[2] * obj.scale + obj.position[2] - camera.z;

  if (z < NEAR) return null;   // behind (or right on top of) the camera

  const u = x / z;
  const v = y / z;
  ...
  return [screenX, screenY, z];
}
Example: camera at (0, 2.2, −1), vertex in the world at (2, 3, 7).
Camera-relative: (2 − 0, 3 − 2.2, 7 − (−1)) = (2, 0.8, 8)
u = 2 / 8 = 0.25 and v = 0.8 / 8 = 0.1
On the 320 x 200 screen (zoom = 200 × 1.2 = 240): screenX = 160 + 0.25 × 240 = 220, screenY = 100 − 0.1 × 240 = 76

Objects behind the camera: if z is tiny or negative, dividing by it would throw the point to the wrong side of the screen. So any vertex with z below 0.4 isn't projected. An edge or triangle that uses it is skipped. On top of that, the camera can't move into coral or jellyfish, and it's kept inside the scene's bounds.

4.3 Line drawing (level 2)

The low-res display is a 2D array, pixelGrid[u][v], of 320 x 200 colors, all starting as the water color. A line on a grid of squares has to become a staircase of pixels. My drawLine uses the incremental method: start at one end, step one column at a time, add the slope to v each step, and round to the nearest row.

Example: a line from (1, 1) to (6, 4). Slope = (4 − 1) / (6 − 1) = 0.6
v values: 1, 1.6, 2.2, 2.8, 3.4, 4.0 → rounded: 1, 2, 2, 3, 3, 4
Pixels filled: (1,1) (2,2) (3,2) (4,3) (5,3) (6,4)

The basic version only works for lines going left to right with a gentle slope (between 0 and 1). The edges of 3D shapes go every which way, so I added two fixes:

  • Lines going backwards: if the line goes right to left (or bottom to top), I swap the two ends first, so it always runs in the increasing direction.
  • Steep lines: if a line changes more in v than in u, stepping by columns would leave gaps. So I step through rows instead and add the inverse slope to u.

I also only loop over the part of a line that's on screen. Otherwise an edge with one end way off to the side could run thousands of useless steps. Once every edge is drawn into the array, I draw each pixel as a 5 x 5 square on the real canvas.

4.4 Triangle drawing and the depth buffer (level 3)

For level 3, each shape is drawn as filled triangles. Each face gets its own brightness, so you can tell the sides of a shape apart. For each triangle:

  1. Bounding box. I find the smallest rectangle around the triangle's three projected corners, so I only check pixels near it, not the whole screen.
  2. Barycentric coordinates. For each pixel center p in that box, I split the triangle into three smaller triangles that meet at p. Each small triangle's area divided by the whole triangle's area gives a weight: α, β, γ. They always add up to 1.
  3. Inside test. If all three weights are 0 or more, the pixel is inside the triangle. If any one is negative, it's outside.
  4. Depth. The same weights mix the three corner depths: depth = α·za + β·zb + γ·zc.
  5. Depth buffer. A second 320 x 200 array remembers the nearest depth drawn so far at every pixel, starting at infinity. I only write the color if the new depth is closer.
Example: triangle A(0, 0), B(4, 0), C(0, 4), and pixel center P(1, 1). The whole area is 8.
α = area(P, B, C) / 8 = 4 / 8 = 0.5   β = area(A, P, C) / 8 = 2 / 8 = 0.25   γ = area(A, B, P) / 8 = 2 / 8 = 0.25
All three are positive, so P is inside. If the corner depths are 4, 8 and 12:
depth = 0.5 × 4 + 0.25 × 8 + 0.25 × 12 = 2 + 2 + 3 = 7

Because of the depth buffer, the order I draw triangles in doesn't matter. A near coral always covers a far jellyfish, with no sorting needed. That's the main advantage over the painter's algorithm, which has to sort everything back to front and still breaks when triangles overlap in depth.

4.5 Color and fog

Each instance has a color. Every frame, that color is mixed toward the water color based on distance, so faraway objects fade into the dark. In level 3, each face's brightness value is applied first.

5. Future work

  • Clipping at the near plane. Right now, a triangle with even one corner behind the camera is skipped completely, so shapes can pop out of view when you get close. Cutting the triangle at the near plane and drawing the part in front would fix that.
  • Rotation. Turning the camera, and letting objects spin (like a rotating jellyfish), would need rotation matrices on top of the scale and translate I use now.
  • Real lighting. Each face has a fixed brightness. Lighting based on which way a face points relative to a light would look more natural.
  • Anti-aliasing. Edges on the 320 x 200 display look jagged. Taking a few samples per pixel and averaging them would smooth them out.
  • More to do. A goal, like collecting pearls or diving to a target depth, would turn the scene into a small game.
